Goal

Add a new “Visitors” menu under the existing “Dashboard” menu in the ITMart24 Admin project. It must collect and display visitor activity from every public and authenticated page of both the User Portal and Vendor Portal.

The feature must support:

1. Live visitors
2. Today’s visitors
3. Last 7 days’ visitors
4. All visitors
5. Visitor locations
6. Page-level analytics
7. Separate User Portal and Vendor Portal reporting

1. Read the existing architecture, authentication, database models, routing, layouts, sidebar/menu configuration, API conventions, environment configuration and documentation in all three projects.
2. Find any existing analytics, activity logging, session tracking, audit-log or notification implementation that can be reused.
3. Follow the existing design system and coding conventions.
4. Do not replace or break existing authentication, middleware, layouts, routes or analytics integrations.
5. Do not install a large third-party analytics platform unless the existing project already uses one.
6. Prefer first-party visitor tracking stored in the existing database.
7. Do not expose database credentials, IP addresses or sensitive tracking information to frontend applications.
8. Update the relevant project documentation after implementation.
9. If Documentation/prompt.txt and Documentation/issues.txt exist, read and follow them. Record genuine restrictions or unresolved problems in issues.txt.

Privacy requirements

- Generate an anonymous first-party visitor ID.
- Do not fingerprint visitors using invasive techniques.
- Do not collect form contents, passwords, OTPs, payment details, query values containing sensitive information or typed text.
- Remove or redact sensitive URL parameters before storing URLs.
- Respect the project’s consent/cookie mechanism if one exists.
- If there is no consent system, use only strictly limited first-party analytics storage and document the behavior.
- Provide a configurable data-retention period.
- Prefer hashing or anonymizing IP addresses after geolocation.
- Never show full IP addresses in the Admin UI. If IP display is necessary, show only a masked version.
- Add an environment-controlled way to disable tracking.
- Exclude Admin project traffic.
- Exclude known health checks, static assets, crawlers and development traffic where appropriate.

Unique visitor and live visitor definitions

Use clear, consistent definitions:

- Page view: one successfully recorded page navigation/view.
- Unique visitor: distinct first-party anonymous visitor ID, with authenticated ID used as an additional association rather than the only identity.
- Session: a group of activity separated by no more than 30 minutes of inactivity.
- Live visitor: a session with activity or heartbeat received within the last 5 minutes.
- Today: use the Admin-configured timezone; default to Asia/Kolkata.
- Last 7 Days: today plus the preceding six calendar days in the configured timezone.

Persist these definitions in shared constants/configuration so backend and frontend calculations remain consistent.

SPA navigation and live presence

Both portals may use client-side navigation. Track:

- Initial page load
- Every valid SPA route change
- Browser back/forward navigation
- Session heartbeat approximately every 30–60 seconds while the page is visible
- Visibility changes
- Page exit using `navigator.sendBeacon()` where supported, with a safe fallback

Avoid duplicate page views caused by React Strict Mode, rerenders or repeated mounting.

Do not send excessive heartbeat requests. Pause heartbeats when the page is hidden and resume safely when it becomes active.

IP and location detection

Resolve the real client IP only from trusted infrastructure:

- Use the direct request address by default.
- Use `X-Forwarded-For`, `CF-Connecting-IP` or similar headers only when the corresponding reverse proxy/CDN is explicitly trusted.
- Never blindly trust arbitrary forwarded headers.

For location:

1. Prefer location headers already supplied by the trusted CDN or hosting platform.
2. Otherwise use an appropriate server-side IP geolocation provider or local GeoIP database.
3. Cache lookup results to prevent repeated external calls.
4. If no provider is configured, save location as “Unknown” without failing visitor tracking.
5. Document required environment variables.
6. Do not fabricate location data.
7. Do not perform geolocation lookups for private, loopback or invalid IP addresses.
